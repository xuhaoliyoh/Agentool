# 《基于大模型的智能体生成工具的设计与实现》答辩演讲稿（代码链路讲解版）

各位老师好，我是软件学院软件工程专业的徐昊，我的毕业设计题目是《基于大模型的智能体生成工具的设计与实现》。上一版汇报更多是在介绍系统功能，这一版我会把重点放到项目真正的核心代码链路上，说明登录认证、用户对话、RAG 切分检索和工具调用这四个部分在后端是怎样运行的。

首先说明整体架构。本项目后端不是把所有逻辑写在 Controller 里，而是按接口层、应用服务层、领域层和基础设施层组织。接口层负责接 HTTP 请求，例如登录接口和对话接口；应用服务层负责一次业务用例的编排，例如登录用例在 `LoginAppService`，对话用例在 `ConversationAppService`；领域层负责业务规则，例如用户密码校验、工具安装记录、RAG 文档状态；基础设施层负责 JWT、消息队列、模型服务、向量库、对象存储和远程工具端点。后面四条链路都按这个调用方向展开。

第一条链路是登录和 JWT。用户登录时，请求先进入 `LoginController.login`，Controller 只做一件事：把 `LoginRequest` 交给 `LoginAppService.login`，然后把返回的 token 包装成统一 `Result` 返回。真正的认证逻辑在应用服务层。`LoginAppService` 首先通过 `AuthSettingDomainService.isFeatureEnabled(AuthFeatureKey.NORMAL_LOGIN)` 检查普通登录开关是否启用，如果后台关闭了普通登录，直接抛出业务异常。然后调用 `UserDomainService.login`，根据邮箱或手机号查询用户，并使用 `PasswordUtils.matches` 对比明文密码和数据库中的加密密码。如果用户不存在或密码错误，返回“账号密码错误”；如果验证通过，就调用 `JwtUtils.generateToken(userEntity.getId())` 生成 JWT。

JWT 生成逻辑集中在 `JwtUtils` 中。它把用户 ID 写入 token 的 subject，设置签发时间 `issuedAt`，再设置 24 小时后的过期时间 `expiration`，最后使用 HMAC 签名密钥进行签名并 compact 成字符串。这里的设计重点是：token 里只保存 userId，不保存昵称、邮箱等完整用户信息，后续需要用户资料时再根据 userId 查询。这样 token 载荷更小，也减少了用户资料变更后 token 内容不一致的问题。

登录后的请求会经过 `UserAuthInterceptor`。该拦截器从 `Authorization` 请求头读取 `Bearer token`，先检查请求头是否存在、格式是否正确，再调用 `JwtUtils.validateToken` 验证签名和过期时间。验证通过后，拦截器调用 `JwtUtils.getUserIdFromToken` 解析 subject，并把 userId 写入 `UserContext.setCurrentUserId`。`UserContext` 底层是 `ThreadLocal`，所以同一次请求后面的 Controller 可以直接通过 `UserContext.getCurrentUserId()` 获取当前用户。请求结束后，`afterCompletion` 会调用 `UserContext.clear()`，避免服务器线程复用时出现用户身份串扰。`WebMvcConfig` 中排除了 `/login`、`/register`、`/health` 等公开接口，其余接口默认都要经过该拦截器。

第二条链路是用户对话。前端工作区发送消息时，后端入口是 `PortalAgentSessionController.chat`，它从 `UserContext` 取出当前用户 ID，然后调用 `ConversationAppService.chat(chatRequest, userId)`。这里 Controller 不直接处理模型、Agent、工具和上下文，是为了让对话主流程集中在应用服务层。

`ConversationAppService.chat` 的第一步是准备对话环境，也就是构造 `ChatContext`。在 `prepareEnvironmentWithModel` 中，系统先根据 sessionId 和 userId 获取会话，确认这次对话属于当前用户；再根据会话中的 agentId 获取 Agent，并检查 Agent 是否可用。如果这个 Agent 不是当前用户自己的，还会读取已发布版本信息，保证用户使用的是安装或发布后的版本。随后系统根据 Agent 绑定的 toolIds 查询当前用户已安装的工具，得到 `mcpServerNames`；再根据工作区中的 `LLMModelConfig` 解析本轮要使用的模型。如果请求中指定了模型，就优先使用指定模型，否则使用工作区模型或用户默认模型。

模型确定之后，系统还会进入高可用服务商选择逻辑。`HighAvailabilityDomainService.selectBestProvider` 会结合用户的 fallbackChain、模型配置和会话信息，选择当前可用的服务商和模型实例。这样对话链路不是简单地拿一个固定 API Key 去调用，而是在运行时完成模型与服务商解析。最后，`ConversationAppService` 把 sessionId、userId、用户消息、Agent、模型、服务商、工具服务名、文件 URL、实例 ID 等信息写入 `ChatContext`。

在真正调用模型前，还需要恢复历史上下文。`setupContextAndHistory` 会根据 sessionId 查询 `ContextEntity`。如果已有上下文，就读取 `activeMessages` 对应的消息实体，而不是每次把全量历史都塞给模型。之后会执行 `applyTokenOverflowStrategy`，把历史消息转换成 `TokenMessage`，结合工作区模型配置中的 `strategyType`、`maxTokens`、`summaryThreshold` 和 `reserveRatio` 构造 `TokenOverflowConfig`。如果历史过长，`TokenDomainService.processMessages` 会按策略保留最近消息、滑动窗口裁剪，或把早期消息压缩成摘要。处理完成后，新的 activeMessages 和 summary 会写回 `ContextEntity`。因此，本项目的上下文治理不是简单拼接字符串，而是把完整消息历史和本轮运行时视图拆开维护。

对话处理器由 `MessageHandlerFactory` 选择。普通 Agent 对话默认使用 `agentMessageHandler`，RAG 专用请求会使用 `ragMessageHandler`。核心流程在 `AbstractMessageHandler.chat`，这是一个模板方法：先创建 SSE 连接，再创建用户消息和助手消息实体，然后初始化 `MessageWindowChatMemory`，把摘要、系统提示词、历史用户消息、历史 AI 消息写入内存，接着调用 `provideTools` 装配工具，最后根据是否流式选择 `processStreamingChat` 或同步处理。这个设计的好处是公共流程统一，具体工具能力由子类扩展。

流式对话时，`processStreamingChat` 会通过 `LLMServiceFactory.getStreamingClient` 创建流式模型客户端，再用 LangChain4j 的 `AiServices.builder(Agent.class)` 构建运行时 Agent。`processChat` 会先保存用户消息并更新上下文，然后调用 `agent.chat(userMessage)` 得到 `TokenStream`。当模型产生部分内容时，`onPartialResponse` 会把增量文本通过 `SseMessageTransport.sendMessage` 发给前端；当生成完成时，`onCompleteResponse` 会设置输入输出 token 数，保存助手消息，更新上下文，发送结束消息，并把本次模型调用结果上报给高可用服务。若模型在中途调用工具，`onToolExecuted` 会先保存已经生成的文本，再保存一条 `TOOL_CALL` 类型消息，并向前端发送工具调用事件。

第三条链路是工具调用。Agent 的工具能力不是写死在提示词中，而是通过 `AgentToolManager` 转成 LangChain4j 的 `ToolProvider`。`AgentMessageHandler.provideTools` 会调用 `agentToolManager.getAvailableTools(chatContext)` 获取当前 Agent 对应的工具服务名，再调用 `createToolProvider`。在这个方法中，系统会逐个处理 mcpServerName，并通过 `DirectToolRuntimeResolver.resolve(serverName, userId)` 解析出当前用户的工具运行时信息。

`DirectToolRuntimeResolver` 会做三件事：第一，通过 serverName 和 userId 查询用户是否安装了这个工具；第二，根据 toolId 和 version 查询 `ToolRuntimeConfigEntity`，也就是工具的运行类型、端点、请求方法、参数 schema、鉴权方式和超时时间；第三，查询当前用户针对该工具保存的凭据 `UserToolCredentialEntity`。最后把 serverName、用户安装记录、运行配置和凭据封装成 `DirectToolRuntime`。这个设计保证了模型只能调用当前用户已安装、且平台有运行配置的工具。

工具运行类型主要有两条路径。第一是 HTTP API。`HttpApiToolProviderFactory` 会把工具定义转成 `ToolSpecification`，执行器是 `HttpApiToolExecutor`。执行时，`HttpApiToolExecutor` 解析模型传来的 `request.arguments()`，如果是 GET 请求就把参数拼到 query 中，如果是 POST 或其他方法就把参数写成 JSON body。`ToolAuthSupport` 会根据配置把鉴权信息加到 Header 或 Query 中，例如 Bearer Token、API Key Header、Basic 认证等。请求返回后，如果状态码大于等于 400，就把 HTTP 状态和 body 返回给模型；如果响应过长，会截断到安全长度，避免污染上下文。

第二条工具路径是远程 MCP SSE。`RemoteMcpToolProviderFactory` 会根据运行配置创建 `HttpMcpTransport`，使用远程 SSE URL 建立 MCP 客户端，再交给 `McpToolProvider` 获取远程工具列表。当前实现中，MCP SSE 连接只支持 query 参数鉴权，这是为了让远程 SSE 连接方式更简单可控。无论是 HTTP 工具还是 MCP 工具，`AgentToolManager.wrapToolExecutors` 都会包一层异常处理：如果工具没有返回内容，或调用抛异常，系统会返回一段明确的失败说明，要求模型不要反复调用同一个失败工具，而是向用户解释工具暂时不可用。这体现了平台对外部依赖失败的治理。

第四条链路是 RAG。RAG 分为入库和检索两部分。入库不是前台同步完成。用户上传文件后，系统发送 `RagDocMessage` 到 RabbitMQ，后台由 `RagDocConsumer.receiveMessage` 消费。消费者会先通过 `FileDetailDomainService.startFileOcrProcessing` 把文件状态切换到处理中，然后读取文件扩展名，通过 `DocumentProcessingFactory.getDocumentStrategyHandler` 选择处理策略，比如 Markdown、Word、PDF 或 TXT。策略执行完成后，系统会完成 OCR 状态，并调用 `autoStartVectorization` 自动启动向量化。

以 Markdown 为例，`MarkdownRagDocumentProcessing` 使用两阶段处理。第一阶段调用 `StructuralMarkdownProcessor` 解析 Markdown AST，构建文档树，并按标题层级和长度进行层次化拆分。拆分出来的原始片段会保存为 `DocumentUnitEntity`，其中 `isOcr=true`、`isVector=false`。这里的核心原则是原文先完整保存，不直接改成向量化版本。

第二阶段由 `DocumentVectorizationOrchestrator` 处理这些原文片段。它先调用 `MarkdownAstRewriter.translateSpecialNodes` 对特殊节点进行翻译或增强，然后使用 `MarkdownContentSplitter.splitIfNeeded` 判断内容是否超过向量长度限制。如果太长，会优先按段落边界切分，其次按句子边界切分，最后才强制截断，并通过 overlap 保持上下文连续性。每个二次切分后的片段都会被包装成 `RagDocSyncStorageMessage`，写入 datasetId、fileId、page、content 和用户嵌入模型配置，再发送到向量化队列。

向量化消费者是 `RagDocStorageConsumer`。它消费 `RagDocSyncStorageMessage` 后调用 `EmbeddingDomainService.syncStorage`。这里会取消息中的 content，而不是重新从数据库读取原文，因为消息中可能已经包含翻译或增强后的向量文本。系统会构造 `TextSegment`，同时写入 metadata，包括 fileId、fileName、documentId 和 datasetId。之后通过用户配置的嵌入模型生成向量，并写入 `embeddingStore`。向量化完成后，原始 `DocumentUnitEntity` 的 `isVector` 会更新为 true，文件整体状态也会随进度推进到完成。

RAG 检索入口在 `RAGSearchAppService.ragSearch`。它先对 request 中的 datasetIds 做权限过滤：用户要么已经安装这个知识库，要么是知识库创建者，否则该 datasetId 会被跳过。有效数据集为空时直接返回空结果。通过权限校验后，系统读取当前用户的嵌入模型配置和聊天模型配置，构造 `HybridSearchConfig`，再调用 `HybridSearchDomainService.hybridSearch`。

`HybridSearchDomainService` 的核心是混合检索。它会先尝试使用 HyDE，把用户问题生成一个假设文档，使向量检索的语义表达更接近文档内容。然后使用 `CompletableFuture` 并行执行向量检索和关键词检索。向量检索由 `EmbeddingDomainService.vectorSearch` 完成，会基于 datasetId 过滤向量库，生成问题向量并查询相似片段；关键词检索则补充传统文本匹配能力。两路结果返回后，系统使用 RRF 融合算法。RRF 的公式是对每个文档累加 `1/(k+rank)`，这里 k 为 60。这样可以把向量检索和关键词检索的排名融合起来，而不强行比较两种检索的原始分数。融合完成后，如果开启 rerank，还会调用 `RerankDomainService` 对候选片段重排序。最后系统根据 documentId 查询 `DocumentUnitEntity`，并按融合分数返回。

RAG 还可以作为 Agent 对话中的内置工具。`RagBuiltInToolProvider` 在 Agent 绑定知识库后定义一个 `knowledge_search` 工具。模型在对话过程中如果判断需要查询知识库，就会调用这个工具，工具内部解析 query、maxResults、minScore、enableRerank 等参数，再调用 `RAGSearchAppService.ragSearch`。搜索结果会被格式化成“文档片段”和“来源信息”，再交给模型生成最终回答。也就是说，RAG 不是孤立页面，而是可以进入 Agent 的工具调用链路，成为智能体回答问题时的知识来源。

最后总结一下，本项目的核心价值在于四条工程闭环。第一，登录身份闭环：登录签发 JWT，后续请求由拦截器验签并恢复用户上下文。第二，对话状态闭环：`ConversationAppService` 装配运行环境，`AbstractMessageHandler` 管理流式生成、消息保存和上下文回写。第三，工具调用闭环：用户安装工具后，系统解析运行配置和凭据，把 HTTP API 或 MCP SSE 工具注册给模型调用。第四，RAG 知识闭环：文件异步解析、层次化切分、向量化入库、混合检索和内置工具共同支撑知识增强。以上就是我的答辩汇报，请各位老师批评指正。
