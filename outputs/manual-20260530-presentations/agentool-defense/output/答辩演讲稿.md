# 《基于大模型的智能体生成工具的设计与实现》答辩演讲稿

各位老师好，我是软件学院软件工程专业的徐昊，我的毕业设计题目是《基于大模型的智能体生成工具的设计与实现》。本课题围绕大语言模型应用落地中的智能体平台建设展开，目标不是实现一个简单的聊天页面，而是完成一个能够支持用户认证、模型配置、智能体创建、工作区对话、工具调用、知识库问答和后台治理的综合性系统。

首先介绍选题背景。随着大语言模型能力快速发展，应用形态已经从单轮问答逐步扩展为能够组织任务、接入外部工具并结合私有知识库的智能体系统。但是在实际工程中，仅仅调用模型接口并不能形成稳定可用的平台。系统还需要处理多用户身份、会话状态、上下文窗口限制、知识检索、工具调用失败、权限边界和后台审核等问题。因此，本文把研究重点放在“如何把大模型能力组织成一个可运行、可扩展、可管理的 Web 平台”上。

本系统的建设目标可以概括为三点。第一，面向普通用户提供从注册登录、配置模型、创建智能体到工作区持续对话的完整闭环。第二，围绕智能体运行过程，支持知识库 RAG 增强和远程 MCP/HTTP 工具接入，使智能体不仅能回答问题，还能结合外部资料和工具能力完成任务。第三，面向管理员提供用户、智能体、工具、知识库、模型服务商和认证配置等治理功能，保证平台能力在多用户场景下具备基本管理边界。

在需求分析方面，论文将功能需求分为七类：用户认证与账户管理、Agent 配置与管理、会话与对话处理、工具接入与执行、RAG 知识库增强、会话上下文治理以及平台管理。非功能需求主要关注可扩展性、可靠性、安全性、性能与可用性。也就是说，系统并不只关注某一次模型调用是否成功，而是关注智能体从创建、配置、运行、增强到管理的完整生命周期。

技术选型上，后端采用 Java 17 和 Spring Boot 3.2.3，结合 MyBatis-Plus、PostgreSQL、pgvector、RabbitMQ、LangChain4j、JWT 和对象存储等技术。PostgreSQL 负责业务数据持久化，pgvector 支撑向量检索，RabbitMQ 用于知识库文件处理的异步任务，LangChain4j 用于模型调用与智能体编排。前端采用 Next.js、React、TypeScript 和 Tailwind CSS，负责工作区、Agent 工作室、知识库、工具市场、模型配置和管理后台等页面。

系统总体架构采用分层设计，并结合领域驱动设计思想组织代码。最外层是接口层，负责接收用户端、管理端和开放接口请求；应用服务层负责业务用例编排；领域层承载核心实体、领域服务和规则；基础设施层负责数据库、消息队列、对象存储、邮件、模型服务和远程工具端点等外部能力。这样的分层可以避免 Controller 中堆积复杂逻辑，也便于将对话、RAG、工具和后台治理等链路分别维护。

功能模块方面，系统主要包括用户认证模块、智能体管理模块、会话与消息模块、模型服务商模块、工具市场模块、RAG 知识库模块、API Key 开放接口模块和管理后台模块。普通用户的主流程是登录后配置模型服务商，创建智能体，绑定工具和知识库，然后在工作区中进行持续对话。管理员侧则负责用户管理、Agent 版本审核、工具审核、知识库审核以及认证策略配置。

数据库设计围绕这些业务对象展开。用户、智能体、智能体版本、工作区、会话、消息、模型服务商、模型配置、工具、工具版本、知识库、知识库文件、文档片段和向量数据共同支撑平台运行。其中消息表保存完整历史记录，上下文相关表维护当前真正参与模型输入的有效消息，知识库相关表则支撑文件上传、解析、切分、向量化、检索和版本发布。

接下来介绍几个核心实现。首先是对话主流程。用户在工作区发送消息后，后端会完成会话校验、智能体配置读取、模型配置解析、历史上下文恢复和增强能力装配。如果启用了知识库或工具，系统会在模型调用前后组织对应能力。模型回复采用流式传输返回到前端，前端可以持续显示增量内容，生成结束后后端会把用户消息、助手回复和上下文状态写回数据库。

大模型调用模块的重点是把模型服务商、模型信息和用户 API Key 解耦。系统支持第三方模型服务商配置，用户可以维护自己的调用凭据。后端在运行时根据会话和智能体配置解析出最终模型参数，再交给模型调用层执行。这样设计可以让平台不绑定单一模型，也便于后续扩展不同服务商或调整模型参数。

工具接入模块采用远程 MCP SSE 和 HTTP API 直连思路。用户提交工具配置后，系统可以进行端点探测，解析工具能力和参数结构，再进入发布和审核流程。智能体对话时，如果需要调用已安装工具，后端会根据工具运行配置构造请求，并处理认证、参数、调用结果和异常提示。论文中特别强调，工具调用失败不能破坏整轮对话，而应返回清晰错误信息并保持会话连续性。

RAG 知识库模块是系统的另一个重点。用户上传文档后，系统不会在前台请求中同步完成全部处理，而是通过 RabbitMQ 将解析、切分和向量化任务异步化。文件会经历上传、OCR 或文本解析、文档单元构建、向量写入等状态。问答时，系统基于向量检索、关键词检索、混合检索和必要的重排序返回相关片段，再将片段作为上下文交给模型生成回答，从而提升回答对私有资料的依赖能力。

会话上下文治理用于解决多轮对话不断增长的问题。模型上下文窗口有限，不能简单把全部历史消息无限拼接。系统在后端引入 Token 处理策略，当历史内容较短时保留有效消息；当内容过长时，可以保留近期消息或将早期内容压缩成摘要。这样既能维持多轮对话连续性，又能控制模型输入规模。消息表保存完整历史，而上下文表维护运行时视图，这是本系统区别于简单聊天 Demo 的重要工程设计。

后台治理与运行支撑主要体现在管理员管理和异步任务处理两个方面。管理员可以维护用户、智能体、工具、知识库、服务商和认证配置。知识库文件处理则通过消息队列和状态机组织，保证上传、解析、向量化和失败状态都有明确记录。这样的设计让系统在面对外部模型、远程工具和文件处理等不稳定因素时，能够做到清晰反馈、状态可追踪和能力可管理。

系统测试部分采用黑盒测试和白盒测试结合的方式。黑盒测试覆盖用户认证、工作区与智能对话、RAG 知识库和 MCP 工具调用，共设计了 18 个主要用例，测试结果均为通过。白盒测试选取登录认证和对话消息处理流程中的关键分支，覆盖登录开关关闭、账号密码错误、登录成功、对话环境不完整和对话成功写回等路径，共 5 条代表性路径，结果也与预期一致。

通过本课题的实现，可以得出结论：该系统较好地把传统 Web 后端工程能力与大语言模型智能体能力结合起来，形成了一个具备用户体系、智能体配置、模型调用、工具增强、知识库增强、会话治理和后台管理的综合平台。它的价值不在于某个单点算法创新，而在于把多项智能体应用所需能力组织成可运行的工程闭环，符合本科毕业设计对需求分析、系统设计、编码实现和测试验证的完整要求。

最后说明不足与后续工作。当前系统仍可以继续加强自动化测试覆盖，对 RAG 检索效果引入更量化的评价指标，并补充运行监控、日志审计、超时重试和生产级安全配置。后续如果继续完善，可以进一步提升系统在复杂业务场景下的稳定性、可维护性和可观测性。以上就是我的答辩汇报，请各位老师批评指正。
