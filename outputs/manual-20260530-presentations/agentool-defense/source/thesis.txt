随着大语言模型技术的迅速发展，智能体系统正由早期的单轮问答工具逐步演进为具备任务组织、知识增强和外部工具调用能力的综合性应用平台。然而，现阶段不少大模型应用在系统集成、业务闭环、知识利用和工程化实现等方面仍存在不足，难以稳定支撑多用户、多场景下的持续使用需求。因此，围绕智能体生成工具开展系统化设计与实现研究，对于推动大语言模型应用落地、提升平台工程复用价值具有重要意义。
本文围绕基于大模型的智能体生成工具展开研究，完成了需求分析、总体设计、数据库设计、核心模块实现和系统测试等工作。系统后端采用基于 Spring Boot 的分层架构，并结合领域驱动设计思想，实现了用户认证、智能体配置、会话处理、大模型调用、MCP 工具接入、检索增强生成和上下文管理等核心模块；数据层基于 MyBatis-Plus、PostgreSQL 与 pgvector，支撑业务数据持久化与向量检索；在对话主链路中，系统实现了流式响应、模型配置解析、知识库混合检索以及远程 MCP/HTTP 工具直连调用等机制，形成了较为完整的智能体运行闭环。
研究结果表明，本文设计并实现的智能体平台较好地融合了传统 Web 后端工程能力与大语言模型智能体能力，具备较强的实践价值和一定的推广意义。后续工作可继续围绕自动化测试覆盖、检索效果量化评估和运行监控体系展开，以进一步提升系统在复杂业务场景下的稳定性与可维护性。

Abstract 
With the rapid development of large language model technologies, agent systems are evolving from single-turn question-answering tools into comprehensive platforms capable of task organization, knowledge enhancement, and external tool invocation. However, many current large-model applications still have shortcomings in system integration, business workflow closure, knowledge utilization, and engineering implementation, making it difficult to meet multi-user and multi-scenario requirements. Therefore, systematic research on agent generation tools is important for promoting the deployment of large language model applications and enhancing their engineering value.
This paper focuses on the design and implementation of an agent generation tool based on large language models, covering requirement analysis, overall design, database design, core module implementation, and system testing. The backend adopts a layered architecture based on Spring Boot and domain-driven design ideas, implementing core modules such as user authentication, agent configuration, session processing, model invocation, MCP tool integration, retrieval-augmented generation, and context management. The data layer uses MyBatis-Plus, PostgreSQL, and pgvector to support business data persistence and vector retrieval. In the main conversation workflow, the system implements streaming response, model configuration resolution, hybrid knowledge retrieval, and remote MCP/HTTP tool invocation, forming a relatively complete execution loop for the agent platform.
The results show that the platform effectively integrates traditional Web backend engineering capabilities with large language model based agent capabilities, and has strong practical value and certain significance for further extension. Future work may focus on automated test coverage, quantitative evaluation of retrieval effectiveness, and runtime monitoring to improve stability and maintainability in more complex business scenarios.

1 文献综述
1.1 研究背景与论文内容
近几年，大语言模型在自然语言理解、文本生成、代码生成和复杂指令执行等方面取得了显著进展，正在推动人机交互系统从传统的信息检索和规则问答，逐步转向面向任务执行的智能体系统 REF ref_2 \h Error: Reference source not found。在这一背景下，系统建设的重点已经不再只是调用单个模型接口，而是如何围绕模型能力构建稳定的业务平台，让模型能够在用户认证、会话状态、工具调用、知识检索和上下文治理等环节中参与协同工作。相关预训练系统研究进一步说明，模型能力的工程化落地同样依赖完备的运行系统与服务组织方式 REF ref_1 \h Error: Reference source not found。
智能体系统的应用价值主要体现在两个方面。第一，智能体能够以自然语言作为统一入口，降低用户使用复杂软件能力的门槛。用户不需要直接理解底层接口、工具参数或知识库结构，就可以通过对话完成信息查询、内容生成和辅助决策等任务。第二，智能体能够把大模型、外部工具、私有知识库和历史上下文组织成连续的执行链路，从而弥补单轮问答在知识时效性、任务连续性和结果可验证性方面的不足。
本文研究的系统正是围绕上述问题展开。系统以“登录认证—模型配置—创建智能体—工作区聊天—会话管理—知识增强与工具增强”为核心业务主线，结合 Spring Boot、MyBatis-Plus、PostgreSQL、pgvector、RabbitMQ、对象存储、Next.js 以及 LangChain4j 等技术，实现用户认证、工作区会话、大模型调用、MCP 工具接入和检索增强生成等能力的统一组织。
从工程实践角度看，智能体平台还需要解决多项传统 Web 系统中并不突出的复杂问题。例如，模型回复 通常以流式方式返回，后端需要在消息保存、中断控制和异常回传之间保持一致；工具调用和知识库检索会引入外部依赖，系统需要处理调用失败、参数缺失、权限边界和结果引用；多轮对话又要求系统在历史消息可用性与模型上下文窗口之间取得平衡，避免无边界扩大输入规模。这些问题共同构成了本文的研究对象。

1.2 国内外研究现状
从大语言模型基础能力来看，国内外研究已经围绕预训练、指令微调、对齐方法和多模态理解形成了较为系统的技术体系。相关综述指出，模型规模、训练数据质量、提示策略和推理增强方法共同影响模型在复杂任务中的表现 REF ref_3 \h Error: Reference source not found；视觉语言预训练研究则进一步拓展了模型对图像和复杂文档的理解能力 REF ref_9 \h Error: Reference source not found。
在智能体研究方面，国外研究较早关注模型与外部环境的交互能力。ReAct 方法将推理过程与行动选择交替组织，使模型能够在执行任务时根据观察结果持续调整后续步骤 REF ref_11 \h Error: Reference source not found；Toolformer 则说明语言模型可以学习在合适位置调用外部工具，从而弥补模型内部知识和计算能力的局限 REF ref_10 \h Error: Reference source not found。面向产业场景的自治智能体综述也表明，工具协同与任务闭环已成为智能体平台的重要发展方向 REF ref_14 \h Error: Reference source not found。
在知识增强方向，检索增强生成技术通过在回答前引入外部文档片段，使模型能够结合私有知识或实时资料生成更可靠的回答 REF ref_12 \h Error: Reference source not found。在融合外部结构化知识方面，知识图谱与大语言模型结合的研究进一步说明，检索与知识组织机制能够有效提升专业问答质量 REF ref_4 \h Error: Reference source not found。与传统全文搜索相比，检索增强生成通常需要完成文档上传、解析、切分、向量化、混合检索、重排序和引用展示等流程，因此它既是算法问题，也是系统工程问题。
在行业应用层面，检索增强和智能体技术已经逐步进入医疗、政务、教育、软件开发和企业知识管理等场景。相关研究表明，在专业领域中直接依赖模型参数知识容易出现知识滞后和事实错误，而引入外部检索、业务规则和人工审核机制后，可以明显提升生成结果的可控性和可信度 REF ref_13 \h Error: Reference source not found。例如在可信政务问答场景中，研究已经证明外部知识与流程约束对回答可靠性具有明显提升作用 REF ref_6 \h Error: Reference source not found。此外，大语言模型在推荐系统解释性等垂直应用方向的研究也表明，模型能力只有在明确的业务约束与知识支撑下，才能形成稳定、可解释的实际系统效果 REF ref_5 \h Error: Reference source not found。
国内关于大语言模型应用平台的研究和实践也在不断增多，主要集中在模型统一接入、知识问答、工作流编排和业务系统集成等方向。已有研究表明，将大语言模型与知识图谱、检索系统或业务数据库结合，可以提升问答系统在专业领域中的准确性和可解释性 REF ref_7 \h Error: Reference source not found。但从完整平台建设角度看，现有研究仍需进一步解决工程集成、权限治理、工具协同与多轮上下文控制等问题。

1.3 本文研究内容
本文围绕基于大模型的智能体生成工具展开研究，主要工作包括以下几个方面。第一，完成系统需求分析，明确普通用户在账号认证、模型配置、智能体管理、工作区对话、工具接入和知识库增强等方面的功能需求，同时明确管理员在认证策略、工具审核、知识库治理和运行支撑方面的治理需求，并分析系统在安全性、可靠性、可扩展性和可用性方面的非功能需求。第二，完成系统总体设计，按照接口层、应用服务层、领域服务层和基础设施层组织系统结构，采用领域驱动设计，并结合数据库表设计、业务流程图和总体架构图明确平台运行边界。第三，完成系统关键模块实现，对用户认证、对话主链路、模型配置、MCP 工具接入、检索增强生成和会话上下文治理等模块进行详细说明，并给出核心流程图和代表性代码。第四，完成系统测试，通过黑盒与白盒方法验证系统主要功能与关键分支路径是否符合预期。

1.4 论文结构安排
本文前置部分为文献综述，主要介绍研究背景、国内外研究现状、本文研究内容和章节安排。正文部分共分为六章：第一章为文献综述，第二章为相关技术介绍，说明系统实现中采用的后端与前端核心技术；第三章为系统需求分析，明确平台的功能需求与非功能需求；第四章为系统总体设计，说明系统架构、功能模块、数据库表设计和核心业务流程；第五章为系统详细设计与实现，重点介绍后端代码逻辑、核心流程图和关键实现片段；第六章为系统测试，采用黑盒与白盒方法验证系统主要功能。

1.5 本章小结
综上所述，大语言模型、智能体、工具调用和检索增强生成等研究，为本文系统提供了较充分的理论基础和技术依据。相关研究说明，单一模型接口并不能直接形成可用的智能体平台，真正影响系统质量的是模型能力、外部工具、知识检索、会话状态、权限控制和工程治理之间的协同关系。本文在吸收已有研究成果的基础上，更关注相关能力如何在同一套后端系统中被稳定组织与实现。
2 相关技术与理论基础
2.1 后端核心技术栈构成
本系统的后端以 Java 17 和 Spring Boot 3 为基础框架，围绕智能体平台的业务目标构建了完整的技术栈。系统在服务端同时引入了 MyBatis-Plus、PostgreSQL、pgvector、RabbitMQ、LangChain4j、对象存储、邮件服务与 JWT 鉴权等能力，用于分别解决业务接口承载、领域流程编排、关系数据持久化、向量检索、异步处理、模型编排、文件流转和用户认证等问题。这样的技术组合并不是简单堆叠，而是围绕“多轮对话、知识增强、工具调用和平台化治理”形成的工程化选型。
从智能体平台建设角度看，后端技术栈需要同时兼顾业务复杂度与模型调用复杂度。一方面，平台要能够支撑登录注册、会话管理、工具安装、知识库管理和后台审核等传统业务功能；另一方面，还要将大语言模型、MCP 工具、RAG 检索和流式返回稳定组织进统一流程。因此，服务端不仅需要普通 Web 系统能力，还需要具备对外部 AI 能力进行装配、约束与治理的能力 REF _Ref227335608 \r \r \h [14]。

图2-1 后端技术栈协同关系图
图2-1展示了本系统后端技术栈之间的协同关系。Spring Boot 承担接口与业务承载职责，DDD 分层结构负责划分用例编排和领域规则，MyBatis-Plus 与 PostgreSQL 负责结构化数据持久化，pgvector 与 LangChain4j 共同支撑向量检索和模型编排，RabbitMQ、邮件与对象存储负责异步处理和文件流转，远程 MCP/HTTP 工具调用机制则负责把外部工具能力接入对话链路。

2.2 Spring Boot 与 DDD 分层架构
Spring Boot 是本系统后端的总体承载框架。项目在 interfaces、application、domain 和 infrastructure 四层结构上展开实现：接口层主要对外暴露 portal 和 admin 两类访问入口；应用服务层负责围绕认证、对话、工具、RAG 和后台治理组织用例流程；领域层负责封装会话、用户、智能体、模型、工具和知识库等核心业务对象；基础设施层则负责数据库、模型服务、远程 MCP/HTTP 工具调用、邮件服务和文件存储等技术细节。这样的设计既符合传统 Java 工程的分层思路，也便于将 AI 相关能力纳入统一架构中。
对于智能体平台而言，分层架构的价值在于把“业务流程编排”和“外部能力接入”分开处理。例如，对话主流程既需要加载会话与用户配置，又需要装配模型、工具和知识检索能力，如果缺少应用层作为协调中心，控制器和底层组件之间会形成过强耦合。通过 Spring Boot 与 DDD 分层结构结合，系统能够在保持接口清晰的同时，为后续扩展新的模型服务商、检索策略或外部工具留下较大空间 REF _Ref229517887 \r \r \h [6]。
从 DDD 的角度看，interfaces 层只处理请求参数、鉴权入口和响应封装，application 层负责组织一次完整用例，domain 层沉淀与业务含义直接相关的校验、状态流转和领域计算，infrastructure 层再把数据库、模型服务、对象存储和外部工具调用封装为可替换的技术实现。这样的边界划分使 Controller 不直接操作底层 Mapper，也使领域规则不依赖具体 HTTP、SSE 或第三方模型协议，从而提高后端代码的可维护性。

2.3 MyBatis-Plus、PostgreSQL 与 pgvector
在持久化层面，系统使用 MyBatis-Plus 处理结构化业务数据，并以 PostgreSQL 作为主要数据库。系统已经建立了 users、user_settings、agents、agent_workspace、sessions、messages、context、user_rags、ai_rag_qa_dataset、document_unit、file_detail 等多组核心表结构。这些表共同支撑用户认证、智能体配置、会话消息、知识库安装关系、文档片段和运行状态管理等业务功能。
除传统关系数据外，系统还需要处理知识库切片的向量检索，因此在 PostgreSQL 上进一步引入了 pgvector 插件作为向量存储基础。文档片段向量被用于 RAG 场景下的语义检索，使平台既保留了关系数据库在事务和管理上的稳定性，又具备了面向知识增强问答的语义召回能力。模型对齐与知识增强研究也强调，外部知识组织方式会直接影响生成结果的稳定性和可信度[3]。
MyBatis-Plus 在本系统中主要承担通用 CRUD、条件构造、分页查询和逻辑删除等基础能力，复杂业务仍由应用服务和领域服务显式组织，避免把业务语义隐藏在 Mapper 层。PostgreSQL 则承担事务一致性、用户数据归属、会话消息持久化和知识库元数据管理等职责；pgvector 在同一数据库中补充向量字段与相似度检索能力，使关系数据和语义检索数据可以在权限校验、数据归属和运维管理上保持统一。

2.4 LangChain4j 与模型编排能力
LangChain4j 是本系统连接大语言模型能力的重要基础组件。对话处理器在执行时会基于用户当前选择的 Provider 和 Model 动态构造同步或流式模型客户端，再结合历史消息、系统提示词和工具提供者生成可执行的会话链路。由于项目不仅需要支持普通对话，还支持 RAG 对话、工具增强对话和预览调试场景，因此模型编排不能停留在“固定调用一个接口”的层面，而需要围绕不同上下文动态组织消息、工具和约束。
从实现目标看，LangChain4j 在本系统中更多承担的是“模型执行中间层”的角色。它既帮助系统统一了消息结构和流式返回形式，也为工具调用、RAG 片段注入和模型协议适配提供了可扩展的抽象能力。大语言模型相关研究指出，模型能力能否真正转化为可控的工程系统，很大程度上取决于编排层是否能够稳定处理提示、状态和外部能力之间的关系[2]。

2.5 RabbitMQ、邮件验证码与对象存储
本系统不是只有 Agent 对话能力，还包含完整的用户认证与文件处理链路。登录注册相关的模块中，发送邮箱验证码依赖验证码服务与邮件发送服务共同完成；其中验证码服务负责图形验证码校验、邮箱频率限制、IP 请求限制和业务类型区分，邮件服务负责依据 SMTP 配置向用户发送注册或重置密码验证码。这样的设计使系统的登录、注册和找回密码流程具备了基本的安全约束与抗滥用能力。
在知识库模块中，文件上传、文件解析和向量化又依赖对象存储与异步处理机制协同完成。系统通过 S3 兼容方式管理文件，RabbitMQ 用于承载需要异步消费的任务处理流程。对于包含知识库和认证能力的综合平台而言，这些基础设施并不是简单的外围附属功能，而是保证系统可用性的重要组成部分。相关研究中关于知识与生成融合的讨论也说明，外部资源链路越长，平台系统越需要以工程化方式保障数据流转和处理稳定性 REF _Ref229518306 \r \r \h [4]。

2.6 MCP 接入机制与前端交互技术
为了让大模型能够调用外部工具，本系统采用远程 MCP/HTTP 工具直连机制。用户创建工具时填写远程 MCP SSE 地址或 HTTP 接口配置，后端先对目标端点进行探测并解析工具定义，审核通过后再进入工具市场供用户安装。对话阶段，系统不托管工具代码，也不执行用户提供的运行命令，而是根据工具运行配置和用户私有凭证直接生成可调用的工具能力，从而完成外部工具与对话主流程的衔接。
前端方面，项目使用 Next.js 15、React 19、TypeScript 和 Axios 组织页面与接口请求，并通过聊天面板、知识库页面、工具市场和后台管理页面承载主要业务交互。登录页、注册页与找回密码页位于 `(auth)` 路由分组下，能够与后端 `/login`、`/register`、`/send-email-code` 等接口形成完整闭环。工具调用研究与 ReAct 相关研究都表明，只有把外部行为链条真正接入到用户可感知的交互界面中，智能体系统的任务执行能力才有实际价值 REF _Ref229517696 \r \r \h [10]。

2.7本章小结
本章围绕后端核心技术栈对系统实现基础进行了说明。可以看出，本系统所使用的技术并非围绕单一聊天页面展开，而是面向完整平台建设组织起来的：Spring Boot 与 DDD 分层提供系统骨架，MyBatis-Plus 与 PostgreSQL 提供业务数据支撑，pgvector 与 LangChain4j 支撑知识检索与模型编排，RabbitMQ、邮件服务、对象存储、JWT 与远程工具接入机制则共同为认证、文件流转、开放能力与工具协同提供保障。这些技术共同构成了后续需求分析、系统设计和详细实现的基础。
3 系统需求分析
3.1 系统建设目标与应用定位
本系统的建设目标并不是实现一个只能进行简单单轮问答的模型演示页面，而是构建一个能够支持用户认证、智能体创建、工作区对话、知识库问答、工具调用和后台治理的综合性大语言模型智能体工具平台。系统把“登录认证—模型配置—创建或选择智能体—发起对话—知识增强或工具增强—保存会话状态”作为核心业务主线，强调平台能力在真实使用场景中的稳定组织。
从应用定位看，系统既解决普通用户的主流程体验，也解决平台管理员的管理需求。普通用户关注的是账户注册登录、智能体配置、多轮对话、知识库问答和工具增强；管理员关注的是认证策略、工具审核、知识库治理和运行参数控制。这样的多角色特征决定了系统在需求设计时必须同时考虑用户操作链路和平台运行链路。

图3-1 系统主要用例图
图3-1将系统参与者划分为普通用户和管理员两类，并围绕登录注册、智能体配置、工作区对话、知识库问答、工具安装使用以及平台管理等能力展示系统的主要用例。
从需求分析角度看，普通用户与管理员并不是两组彼此孤立的功能使用者，而是分别对应“业务使用链路”和“平台治理链路”两套不同目标。前者关注登录、创建智能体、发起对话、绑定知识库和调用工具的连续体验，后者关注模型可用性、工具审核状态、知识库资源质量与系统运行边界的一致性。只有同时满足两类角色诉求，平台才能既可用又可控。
因此，论文中的需求分析不能停留在简单用例枚举层面，还需要把用户请求在系统中的状态流转方式说明清楚。围绕这一点，本文进一步补充了工作区主业务链路需求流程，并对关键约束条件进行细化，以说明系统后续为何必须采用统一对话入口、统一状态回写与统一异常反馈的设计方式。

3.2.1 用户认证与账户管理需求
用户认证是系统运行的基础前提。系统需要支持邮箱注册、邮箱密码登录、图形验证码、邮箱验证码、密码重置、用户资料维护和默认模型配置等功能。认证模块不仅承担“让用户进入系统”的职责，还负责建立用户身份、会话归属和后续权限校验基础。
为了保证认证流程安全性，系统必须具备验证码防刷、密码加密存储和账户状态校验能力。登录成功后，系统统一签发 JWT 令牌供受保护接口鉴权使用；注册成功后，系统还需要同步写入用户配置记录，保证新用户具备继续使用模型、知识库和会话能力的基础运行条件。

3.2.2 Agent 配置与管理需求
智能体是平台的核心业务对象，也是把模型配置、工具能力和知识增强能力组织到统一业务单元上的关键枢纽。系统需要支持用户创建、编辑、启用和查看智能体，并维护名称、角色描述、系统提示词、欢迎语、工作区关系、工具绑定和知识库绑定等信息。
只有在智能体维度完成运行配置聚合，后续会话、模型选择、工具注入和知识检索能力才能以统一方式挂接到一次对话请求之上。因此，智能体管理不仅是一个配置界面，更是系统运行主链路的重要前置条件。

3.2.3 会话与对话处理需求
会话模块承担系统的运行主线。系统需要支持会话创建、消息发送、消息历史查询、会话切换以及流式返回，并在后台维护消息落库、上下文更新、连接超时清理和手动中断等能力。对于一个真正可用的智能体平台而言，会话并非简单消息列表，而是连接用户身份、Agent 配置、模型调用和知识检索的统一业务载体。

3.2.4 工具接入与执行需求
为了使智能体具备处理复杂任务的能力，系统需要支持远程 MCP 工具和 HTTP 工具的接入、探测、审核、安装、凭证保存与运行时调用。工具能力的重点不只是“能否发起请求”，还包括失败时能否保持主链路稳定、不同用户之间的工具凭证能否隔离，以及工具版本与审核状态能否被后台统一管理。

3.2.5 RAG 知识库增强需求
当用户问题依赖私有资料和业务文档时，仅依靠大模型参数无法保证结果准确性，因此系统必须具备知识库上传、文件处理、切片向量化、知识库发布、用户安装和 RAG 对话等能力。知识增强的目标并不是单纯“多加一点上下文”，而是通过结构化的数据集管理与检索策略控制回答依据来源，减少模型幻觉 REF _Ref229517702 \r \r \h [12]。

3.2.6 会话上下文治理需求
随着多轮对话持续进行，系统需要解决上下文长度不断膨胀、历史信息丢失和模型输入超过窗口限制等问题。因此，本系统需要支持会话级上下文裁剪和摘要压缩：一方面保留当前会话中与问题最相关的历史消息，另一方面在历史内容过长时生成摘要并回写上下文状态，从而兼顾对话连续性和模型调用稳定性。

3.2.7 平台管理需求
除面向普通用户的门户端功能外，系统还需要提供后台管理能力，用于围绕用户、模型、工具、RAG 和认证配置开展治理工作。后台管理虽然不直接参与模型生成，但决定了模型资源、工具上架、知识库审核和认证方式等支撑能力是否可控，因此本系统必须具备清晰的接口分层和权限边界。

3.3 非功能需求分析
3.3.1 可扩展性需求
系统面向持续演进的应用场景，因此在架构上必须允许模型服务商、检索策略、工具类型和后台治理能力继续扩展。当前代码通过分层结构和服务拆分为后续扩展预留了较好的边界。

3.3.2 可靠性需求
对智能体平台而言，可靠性不仅体现为接口能否访问，还体现为会话是否连续、流式连接是否稳定、工具调用是否可恢复、模型配置错误是否能够被清晰提示。SSE 连接治理、上下文裁剪、外部服务状态检查和异常返回机制等实现都说明系统对可靠性有明确需求。

3.3.3 安全性需求
系统同时涉及用户密码、邮箱验证码、知识库文件、工具运行配置和会话数据访问，因此安全性要求较高。认证模块需要保证密码加密存储与验证码限流，工具模块需要保证调用边界清晰，知识库模块需要保证用户数据边界，会话模块则需要保证不同用户与不同 Agent 之间的数据隔离。

3.3.4 性能与可用性需求
本系统面向交互式场景，用户对响应时延和过程反馈十分敏感。因此，系统不仅要追求模型完整回答的正确性，还要通过流式消息、分阶段状态提示和上下文治理降低等待感，保证常见场景下的交互流畅性。

3.3.5 非功能需求总结
系统的非功能需求主要体现在可扩展性、可靠性、安全性和可用性四个方面。由于智能体平台同时依赖模型服务、外部工具和异步处理链路，非功能需求对系统能否真正落地具有同等重要性。
进一步看，可测试性也是本项目不可忽略的隐含非功能需求。由于平台同时依赖模型服务、对象存储、消息队列和远程工具端点，若系统不能把关键状态暴露为可追踪的表字段、日志信息或接口返回，则后续调试、测试和答辩演示都难以支撑。因此，本项目在设计上强调“状态可见、异常可解释、链路可恢复”，这也是后文测试章节能够给出表格化结果的前提。

3.4 本章小结
本章围绕系统建设目标、用户认证、Agent 配置、会话处理、工具接入、RAG 和后台治理等方面分析了系统需求。可以看出，本系统的需求边界已经超出单一 Agent 对话场景，而是形成了以认证为入口、以工作区会话为主线、以模型、工具和知识为核心能力的综合平台需求结构。

4 系统总体设计
4.1 系统设计目标与原则
在完成需求分析后，系统总体设计的任务是将多角色、多模块的业务目标转化为清晰、可实现、可扩展的技术结构。结合项目实际代码与部署配置，本系统在总体设计上遵循模块解耦、统一接口、运行可控和便于扩展四项基本原则。模块解耦要求认证、会话、模型、工具、RAG 与后台管理能够相对独立演进；统一接口要求不同请求入口和不同执行链路在应用层得到集中组织；运行可控要求对会话、模型和外部服务状态进行持续治理；便于扩展则要求系统对新增服务商、工具或业务模块保持足够兼容性。

4.2 系统总体架构设计
从整体结构上看，系统采用前后端分离架构。前端基于 Next.js 和 React 实现登录注册、工作台、知识库、工具市场和后台管理等页面；后端基于 Spring Boot 提供统一的业务接口、会话编排、模型调用、知识检索和工具运行协调能力；数据库、中间件与文件存储则构成底层基础设施。用户操作通过 HTTP 与 SSE 请求进入系统后，由后端完成集中编排并把结果返回到前端页面。


图4-1 系统总体架构图

图4-1展示了本项目的系统总体架构。整体上，系统采用分层组织方式，而不是简单的串行流程结构：最上层为表现层，负责承载用户前端和管理后台的人机交互；中间为平台核心服务层，用于统一接收请求并协调各类业务能力；其下为功能模块层，进一步划分为用户认证与权限、会话与智能体、知识库问答以及工具接入与调用等核心模块；最底层为技术支撑层，提供数据持久化、模型编排、检索增强以及工具运行时等底层能力支持。这样的架构能够清晰体现系统“上层负责交互、中层负责编排、下层负责支撑”的组织关系。
其中，平台核心服务并不直接承担所有细节实现，而是作为统一枢纽，将不同功能模块与对应技术栈进行解耦连接。例如，会话与智能体功能依赖模型编排能力，知识库问答功能依赖检索增强能力，工具接入功能依赖外部工具运行时支持，而认证与权限等基础业务则依赖数据库持久化能力。该架构既保证了系统各模块职责清晰、边界明确，又为后续扩展新的模型服务、工具类型或知识库能力提供了良好的可维护性和可扩展性，这样的设计更符合本项目代码中的真实职责划分。

4.3 功能模块设计
依据系统实现情况，本文将平台划分为用户认证与账户管理模块、智能体配置与管理模块、会话与对话处理模块、大模型调用与模型配置模块、MCP 工具接入模块、检索增强生成模块以及后台治理模块七类核心模块。这样的划分既能反映代码中的真实边界，也便于在论文中清楚说明各模块的职责分工。
其中，用户认证负责建立身份和权限边界，智能体配置负责聚合运行参数，会话与对话处理负责串联主业务流程，大模型调用负责解析和构建模型运行时，MCP 工具接入负责外部能力拓展，检索增强生成负责提供资料支撑，后台治理则保证平台运行可控。

系统的数据设计围绕用户、智能体、工作区关系、会话、消息、上下文、知识库和工具安装关系等核心对象展开。用户是所有业务数据的归属主体；智能体承担模型、知识和工具配置的聚合作用；会话、消息与上下文共同构成对话持久化基础；知识库与工具安装关系则分别为检索增强生成和外部工具调用提供结构化支撑。

4.5 核心业务流程设计
系统的核心业务流程可以概括为“请求进入、环境装配、链路选择、模型执行、状态更新、结果返回”六个阶段。请求进入后，系统首先根据用户身份和会话标识读取当前业务上下文，然后装配智能体配置、模型配置、工具能力和知识检索能力，再依据具体场景选择普通对话、工具增强对话或知识增强对话链路。执行完成后，系统统一完成消息回写、上下文更新、必要的运行状态记录与前端响应。


图4-2 系统核心业务流程图

图4-2展示了系统在不同对话场景下的核心业务流程。系统并不是将所有请求按照固定顺序串行处理，而是采用“统一入口、分阶段处理、按场景分支、统一出口”的组织方式。用户请求进入系统后，首先完成会话创建或定位、智能体配置加载、模型参数读取以及历史上下文装配等准备工作；随后，系统根据当前请求类型判断应进入普通对话、知识库增强或工具调用增强等不同业务链路，从而保证不同场景都能复用同一套会话主框架。
在各分支完成自身处理后，系统会重新汇聚到统一的结果生成阶段，完成提示词组织、模型调用、消息保存以及会话状态更新，最终将结果返回给前端。这样的流程设计既体现了平台在业务层面的统一调度能力，也保证了知识库检索、工具调用和普通问答等能力之间的解耦，便于后续扩展新的对话类型或增强能力，同时提高了系统整体的可维护性与可扩展性。
4.6 接口设计思路
接口层主要划分为普通用户接口和后台管理接口两类。普通用户接口负责登录注册、会话聊天、知识库管理、模型选择和工具安装等业务，后台管理接口负责认证配置、工具审核、知识库治理与平台运行参数维护。这样的接口分层使系统既能保证主业务链路流程清晰，也能保留必要的治理边界。
在接口设计上，系统尽量保持“入口统一、参数清晰、返回一致”的原则。对话类接口以会话和智能体为上下文，配置类接口以用户和工作区为上下文，管理类接口则以平台资源为上下文，从而减少跨模块歧义。

4.7 本章小结
本章从总体架构、模块划分、数据库设计和业务流程等方面，对系统总体设计进行了说明。可以看出，本系统已经形成了较为清晰的工程化结构：用户认证构成统一入口，会话对话构成运行主线，模型、工具和知识构成核心能力层，后台管理则提供必要的治理支撑。

5 系统详细设计与实现
5.1 用户认证与账户管理模块实现
5.1.1 登录与注册功能
用户认证与账户管理模块是系统的统一入口，其后端实现遵循控制层、业务层和数据访问层分离的思路。前端提交登录或注册请求后，控制层负责接收参数并完成基础校验，业务层负责组织认证规则、状态判断和流程编排，数据访问层负责用户信息、用户配置等数据的读写。这样处理后，页面只承担交互职责，真正决定“能否登录、能否注册、登录后写入哪些数据”的逻辑均集中在后端服务中，更符合 Spring Boot 与 DDD 分层架构下的职责划分。
登录功能的核心流程包括账号识别、密码校验和身份令牌签发三个步骤。系统接收到用户输入后，先判断当前认证方式是否启用，再根据邮箱信息查询用户主体数据，随后对用户输入密码与数据库中的加密口令进行比对，校验通过后生成登录令牌并返回前端。前端在后续访问工作区、知识库、工具配置等受保护页面时，需要携带该令牌完成身份验证，因此登录模块不仅是页面入口，也是后续全部业务能力的权限起点。

public String login(LoginRequest loginRequest) {
    if (!authSettingDomainService.isFeatureEnabled(AuthFeatureKey.NORMAL_LOGIN)) {
        throw new BusinessException("普通登录已禁用");
    }
    UserEntity userEntity =
            userDomainService.login(loginRequest.getAccount(), loginRequest.getPassword());
    return JwtUtils.generateToken(userEntity.getId());
}

上述代码体现了登录流程中最关键的三步：认证开关检查、用户查询与密码比对、身份令牌生成。控制层并不直接操作数据访问对象，而是通过应用服务和领域服务分层完成核心业务逻辑，这也是系统保持后续扩展能力的重要原因。
从真实实现可以看到，登录流程并不是控制器直接查表，而是先由应用服务检查认证功能开关，再交由领域服务完成账号与密码校验，最后统一生成令牌。这种结构使认证策略控制、密码校验规则和用户状态判断可以独立演进，也更便于在后台治理模块中统一开闭认证入口。
注册功能在流程上比登录更长。系统需要先验证图形验证码与邮箱验证码，再检查当前是否允许开放注册，之后创建用户主体记录，并同步初始化用户默认配置。后端在写入用户表的同时，还会写入用户配置表，用于保存默认模型、嵌入模型等后续运行参数。这样可以保证新用户注册完成后，不只是获得一个账号，还具备进入智能体平台继续使用模型、知识库和对话能力的基础运行条件。

5.1.2 邮箱验证码与密码重置功能
邮箱验证码功能用于支撑注册与密码重置等关键场景。用户请求发送验证码时，后端不会直接发信，而是先完成图形验证码校验、发送频率限制和业务类型判断，然后再生成随机验证码并写入临时存储。邮件发送服务读取 SMTP 配置后完成实际投递，因此“是否允许发送”和“如何发送邮件”被划分为两个独立责任，有利于后续维护。
为了避免验证码接口被频繁调用，系统在后端增加了多重限制策略，包括客户端请求间隔、单日发送上限和业务类型隔离。注册验证码与重置密码验证码虽然都通过邮箱触达用户，但在后端存储时会按业务场景分别管理，防止不同功能之间出现验证码串用的问题。这种设计提高了认证流程的稳定性，也减少了恶意调用带来的资源消耗。
密码重置流程建立在验证码机制之上，但校验条件更严格。系统只有在确认用户账号存在后才允许发送重置验证码；用户提交新密码时，后端还会再次核对验证码是否有效，校验通过后才更新数据库中的密码字段。这样可以避免未注册邮箱进入重置流程，也能防止旧验证码或错误验证码绕过校验直接修改密码。

5.1.3 用户设置与认证配置
登录成功后，用户相关能力并不会停留在“身份校验”层面，而会继续延伸到系统配置层。用户可以在个人设置中维护基础资料、默认模型、默认嵌入模型和 OCR 模型等信息，这些配置会直接参与后续的智能对话、知识检索和文件处理流程。因此，用户设置模块本质上也是后端运行参数管理模块的一部分。
从后端实现来看，用户设置的更新并不是简单覆盖一条展示数据，而是通过业务层统一写入用户配置记录，并在后续会话准备、知识库检索和文件处理时被重新读取。这样做的好处是，模型调用相关参数始终从数据库中的正式配置获得，而不是零散依赖前端临时传值，从而提高系统的一致性和可维护性。

5.2 对话主流程与流式传输实现
5.2.1 对话入口与环境准备
对话主流程是本项目的核心业务链路。用户在工作区向某个智能体发送消息后，请求会先进入后端统一对话入口，再由业务层完成会话校验、智能体读取、工作区模型配置读取以及上下文恢复等准备工作。换言之，用户表面上只是在聊天框中输入一句话，但后端在真正调用模型之前，已经先把用户、会话、智能体、模型、工具和知识库等运行要素组织到同一条处理链中。
环境准备阶段首先要确认当前消息属于哪个会话、哪个用户以及哪个智能体。随后系统读取该智能体所在工作区的模型配置，并结合用户安装的工具、已绑定的知识库和历史消息，生成一次对话所需的完整运行上下文。如果当前使用的是已发布版本智能体，系统还需要优先读取稳定版本信息，以保证实际运行结果与用户看到的配置保持一致。
在后端实现上，这一阶段通常会把会话信息、用户消息、模型参数、附件地址和上下文历史整理成统一的运行对象，并作为后续处理器共享的数据基础。这样设计后，后面的消息处理、模型调用、工具注入、知识检索和消息持久化都不需要重复向上游索取参数，而是围绕同一份上下文连续执行，体现出 DDD 分层下“应用服务统一编排、领域能力分模块完成”的实现特点。

public SseEmitter chat(ChatRequest chatRequest, String userId) {
    ChatContext environment = prepareEnvironmentByRequestType(chatRequest, userId);
    MessageTransport<SseEmitter> transport =
            transportFactory.getTransport(MessageTransportFactory.TRANSPORT_TYPE_SSE);
    AbstractMessageHandler handler = messageHandlerFactory.getHandler(chatRequest);
    SseEmitter emitter = handler.chat(environment, transport);
    chatSessionManager.registerSession(chatRequest.getSessionId(), emitter);
    return emitter;
}

该段代码概括了对话主链路的核心思想：先构造统一运行上下文，再根据场景选择处理器，最后由处理器完成模型调用、消息保存和结果返回。通过这种方式，不同对话模式可以在统一骨架下复用大量基础逻辑。

图5-10展示了系统从接收对话请求到准备完成运行环境的整体关系。与普通聊天页面直接转发模型请求不同，本项目会先完成会话、模型、工具和知识库等信息的装配，再进入真正的生成阶段，因此对话功能具备更强的平台化特征。

5.2.2 对话处理组织方式
为了避免不同对话场景的逻辑全部堆积在同一个服务中，系统在后端采用了统一骨架加差异化处理的组织方式。普通对话、知识库问答、预览对话等场景都遵循相似的处理步骤，例如创建连接、保存用户消息、装配历史上下文、准备模型输入、接收模型输出以及回写会话数据，只是在检索增强、执行追踪和工具注入等环节存在差异。
这种设计的价值在于把“共性流程”和“特性流程”拆开管理。共性流程由统一的消息处理骨架负责，保证消息保存、上下文恢复、流式传输和异常处理的实现方式保持一致；特性流程则由不同业务场景分别扩展，从而避免某个新能力加入后影响原有全部对话逻辑。对于智能体平台而言，这比把所有判断写在单一聊天方法中更容易扩展和维护。
从业务角度看，后端真正需要保证的是：无论用户发起的是普通问答、带知识库的问答，还是针对未发布草稿的预览对话，系统最终都能走完“接收请求、组织输入、生成回复、保存结果”的主链路。统一处理骨架正是为了解决这一问题，使不同对话模式在共享基础能力的前提下保留各自差异。
这种后端组织方式也使后续新增功能的成本明显降低。例如，当系统未来需要增加新的对话模式时，只需在现有主链路上补充差异步骤，而不必重新实现消息保存、上下文处理和连接管理等底层公共能力。
通过上述设计，对话模块既保持了结构清晰，又能支撑普通对话、知识问答和工具增强等多种业务场景，是全文中最能体现系统工程化程度的关键部分。

5.2.3 流式响应与会话状态维护
在用户体验层面，系统采用 SSE 实现流式响应。后端在开始生成前先建立长连接，再将模型返回的增量内容持续推送给前端，使用户能够边生成边查看回答结果。相较于一次性返回完整答案，流式交互更符合智能体系统的实际使用习惯，也便于在工具调用、知识检索等中间阶段向用户展示运行状态。
流式传输并不是单纯的输出技巧，它还需要和后端会话治理配合完成。连接建立后，系统会记录当前活跃会话，并为超时、中断和异常情况注册回调处理；生成过程中如果用户主动停止输出，后端需要及时结束连接并释放会话状态，防止无效会话继续占用资源。这样处理后，流式对话不仅能实时输出内容，也具备可中断、可恢复和可清理的运行特征。
消息持久化则是流式对话的另一关键点。系统会在生成前先保存用户消息，在生成完成后写入助手消息，并同步更新上下文记录与消息顺序。这样一来，前端看到的实时输出和数据库中的历史消息保持同源，页面刷新后仍可恢复会话内容，不会出现“页面显示过、数据库却没有保存”的状态不一致问题。

5.3 大模型调用与模型配置实现
大模型调用模块负责把用户配置、工作区配置和实际模型请求连接起来。系统支持用户维护多种模型服务商和不同模型条目，后端在每次对话开始前都会根据当前智能体和工作区配置，解析本轮应使用的模型、调用地址、密钥信息以及上下文参数，而不是把模型写死在业务代码中。
模型选择遵循由近到远的优先级规则。若当前工作区为某个智能体单独设置了模型参数，则优先使用该配置；若存在更明确的指定模型，则按指定配置执行；若都不存在，则回退到用户默认模型。除了模型标识外，温度、最大输出长度和上下文保留策略等参数也会在这一阶段一并确定，从而保证一次对话所需的全部模型信息在正式调用前已经准备完毕。

private ModelEntity getModelForChat(LLMModelConfig llmModelConfig,
        String specifiedModelId, String userId) {
    String finalModelId = specifiedModelId != null && !specifiedModelId.trim().isEmpty()
            ? specifiedModelId : llmModelConfig.getModelId();
    ModelEntity model = llmDomainService.findModelById(finalModelId);
    if (finalModelId == null) {
        String userDefaultModelId = userSettingsDomainService.getUserDefaultModelId(userId);
        model = llmDomainService.getModelById(userDefaultModelId);
    } else if (model == null) {
        model = llmDomainService.getModelById(finalModelId);
    }
    model.isActive();
    return model;
}

在后端实现上，模型解析和模型调用被分成两个步骤处理。前者负责从数据库读取模型与服务商记录，并校验当前配置是否可用；后者负责依据解析结果构造同步或流式模型客户端。这样做可以让控制层和对话主流程只依赖统一的调用能力，而不需要关心具体服务商差异、接口地址拼接方式和鉴权细节，体现出 Spring Boot 服务治理与 DDD 分层编排相结合的设计思路。
该模块还承担了重要的状态检查职责。例如模型是否启用、服务商配置是否完整、密钥是否缺失、目标模型是否可访问等问题，都会在正式调用前被统一拦截并返回明确错误信息。这样可以避免错误一路传递到前端展示层，减少由于模型配置异常引起的无效请求和排查成本。
在本项目中，LangChain4j 主要作为模型调用与流式输出的中间层，负责把后端准备好的模型配置转换为统一客户端能力。借助这一层抽象，普通问答、知识库问答和工具增强问答都可以共用同一套模型调用方式，而消息保存、上下文更新和异常处理仍由系统自身后端逻辑掌控。


图5-12 模型配置页面效果截图

模型调用结束后，系统还会把本轮消息内容、输入输出标记和上下文变化写回数据库。因此，模型配置模块并不是孤立的参数页，而是连接用户设置、对话执行和消息持久化的关键中间层。
进一步结合后端装配过程可以发现，模型调用前并不是只完成一个modelId的解析，而是要连续确定工作区模型配置、用户默认模型回退关系、当前服务商可用性以及高可用切换后的实际执行实例。也就是说，系统在真正创建模型客户端之前，已经先把“应当使用哪个模型”“应当连接哪个服务商”“当前配置是否允许执行”这几类问题逐层消解，从而避免后续消息处理阶段再次夹杂大量配置判断逻辑。
与此同时，系统还会把原始模型、实际执行模型、原始服务商、当前服务商以及实例标识统一写入ChatContext，供后续处理器直接复用。这样做的意义在于，后面的普通问答、知识库问答和工具增强问答虽然业务场景不同，但都可以围绕同一套模型运行环境展开处理，并在需要追踪模型切换或排查调用异常时保留完整上下文依据。图5-13正是在这一基础上，对模型配置解析到客户端构造的关键中间环节进行了进一步抽象。

5.4 MCP 工具接入实现
MCP 工具接入模块用于让智能体在对话过程中调用外部能力。结合项目当前的重构结果，系统已经不再采用网关转发或容器托管的复杂方案，而是以“远程 MCP 端点或 HTTP 接口的直接调用”为主要实现方式。平台负责完成工具登记、端点探测、审核上架、用户安装和对话注入，不负责托管第三方工具代码，从而显著简化了系统实现。


图5-14 工具配置与调用页面效果截图

工具接入的第一步是运行配置探测。用户在后台填写工具名称、说明、调用地址、请求方式和鉴权信息后，后端会先对目标端点进行可用性检查，并尝试解析工具定义。只有探测成功的工具才会进入待审核状态，同时当前运行配置会被单独保存，便于后续版本管理和问题追踪。这一设计说明工具模块并不是“填完地址就立即可用”，而是先经过后端校验后再进入市场流通。
工具上架后，普通用户并不是直接调用原始工具，而是先安装某个已审核版本。安装关系、运行配置快照和个人凭证信息由后端分别保存，从而保证同一个工具在不同用户之间既可以共享公共定义，又能拥有各自独立的私有鉴权信息。这种处理方式既满足了平台管理需求，也避免在公共配置中泄露用户密钥。
在对话阶段，系统会根据当前智能体已绑定的工具列表，结合用户安装关系解析出真正可用的工具。若工具类型为远程 MCP，则后端直接建立与目标服务的通信连接；若工具类型为 HTTP 接口，则后端按既定请求结构发起调用，并把返回结果整理为模型可理解的内容。整个过程不再依赖额外的网关或容器调度链路，从而更符合当前项目“简化实现、保证可运行”的技术路线。
工具调用的关键不只是“能否发起请求”，还在于后端是否能在失败时保持主链路稳定。为此，系统在工具执行阶段增加了超时控制、异常拦截和结果包装机制。当远程工具不可达、凭证缺失或返回内容异常时，后端会向对话流程返回可识别的失败信息，而不会让整个聊天过程直接中断。这样既提高了工具能力的可用性，也降低了外部依赖对主业务链路的影响。
从系统结构上看，MCP 工具模块把后台管理、市场分发、用户安装和对话调用串联成了一条完整后端链路。它既保留了工具审核与版本化管理能力，又通过直接调用方式降低了部署复杂度，是本项目当前技术实现中较为典型的简化重构案例。

5.5 RAG 知识库检索实现
RAG 知识库检索模块由知识库管理、文件处理、混合检索和回答生成四部分组成。用户在前端创建知识库并上传文件后，后端会将知识库主体、文件状态和文档分片分别写入数据库中的不同表结构中，以便后续完成文件解析、向量化存储和问答调用。该模块既依赖 PostgreSQL 进行结构化数据保存，也依赖 pgvector 保存向量检索所需的数据结果。
文件上传后的第一条主链路并不是立即问答，而是后台预处理。系统会先记录文件基本信息和处理状态，再通过消息队列异步触发文档解析任务。消费者根据文件类型选择对应处理方式，完成文本提取、必要的 OCR 识别、内容切分和状态回写。只有当分片数据和向量数据准备完成后，该文件才真正具备被检索和被引用的条件。
检索请求到达后，后端首先检查当前用户对目标知识库是否具有访问权限，然后读取默认嵌入模型和相关检索参数，构造本次检索所需的运行配置。这样做的目的是确保知识库问答并不是对所有数据的无差别搜索，而是建立在用户权限、知识库归属和模型配置均正确的前提下执行。
在检索方法上，系统采用向量检索与关键词检索结合的混合策略。向量检索负责处理语义相近的内容召回，关键词检索负责补充字面匹配能力，两路结果再由后端进行融合排序，必要时进一步重排。相较于单一检索方式，混合检索更适合论文资料、产品说明等复杂文本场景，能够提高返回片段的相关性和稳定性。
检索得到的文档片段不会直接原样返回，而是先被整理为两部分内容：一部分作为引用来源返回前端展示，便于用户查看回答依据；另一部分被拼接到模型提示信息中，用于约束模型基于资料生成回答。这样，知识库问答的后端实现实际上完成了“文件处理、权限校验、检索召回、引用展示和回答生成”的完整组合流程，而不只是简单的全文搜索。

HybridSearchConfig config = HybridSearchConfig.builder(validDatasetIds, request.getQuestion())
        .maxResults(request.getMaxResults())
        .minScore(adjustedMinScore)
        .enableRerank(request.getEnableRerank())
        .candidateMultiplier(adjustedCandidateMultiplier)
        .embeddingConfig(embeddingConfig)
        .enableQueryExpansion(request.getEnableQueryExpansion())
        .chatModelConfig(chatModelConfig)
        .build();
List<DocumentUnitEntity> entities = hybridSearchDomainService.hybridSearch(config);
return DocumentUnitAssembler.toDTOs(entities);

上面的代码对应了系统当前混合检索的核心思路：向量召回、关键词召回、结果融合和可选重排。检索得到的文档片段一部分返回前端展示引用来源，另一部分被拼接到提示词中约束模型回答。
同时，RagMessageHandler 在执行检索时还会向前端发送“开始检索”“检索完成”“开始生成回答”等阶段消息，并将轻量级引用片段作为 payload 回传。这使知识库问答不再只是黑盒调用，而具备了可观测的分阶段反馈能力。

5.6 会话管理与上下文处理实现
会话管理模块负责保持多轮对话的连续性，其后端数据基础主要由会话表、消息表和上下文表组成。会话表保存每个聊天主题的归属关系，消息表保存用户消息和助手消息的完整历史，上下文表则保存下一轮模型调用所需要保留的有效消息范围。三者分工明确，能够同时满足历史回看和运行时恢复的需求。
当用户进入某个智能体页面时，系统可以读取已有会话列表，也可以自动创建新的默认会话。新建会话后，后端会写入会话主体数据，并在必要时补充初始提示信息；删除会话时，则会同步清理相关消息和上下文记录，避免数据库中残留无效数据。这样设计后，会话不再只是前端的页面切换标签，而是具有完整生命周期管理的后端业务对象。
多轮对话带来的核心问题是历史消息会不断增长，而模型的上下文窗口始终有限。为解决这一问题，系统在后端引入了上下文治理策略：当历史消息较短时，可以直接保留全部有效内容；当消息过长时，则按设定规则保留近期消息，或将早期内容压缩为摘要后继续参与后续对话。这样既能维持上下文连续性，也能控制模型输入规模。

从数据实现角度看，消息表承担的是完整历史记录职责，而上下文表承担的是运行时视图职责。后端每次保存新消息后，都会同步更新当前可参与下一轮生成的有效消息列表；若发生上下文压缩，还会把压缩后的摘要结果一并写回。借助这种结构，系统无需在每次请求时反复扫描全部历史消息，就能较快恢复本轮真正需要送入模型的上下文内容。
会话治理模块与对话主流程、模型配置和消息持久化紧密相连。它保证了用户刷新页面后仍能查看历史消息，也保证了系统在上下文过长时能够通过后端策略完成受控裁剪。对于多轮智能体平台而言，这种实现比简单拼接全部历史文本更加稳定，也更符合工程化应用的实际要求。

5.7 后台治理与运行支撑实现
除了面向普通用户的主流程外，平台还需要后台治理与运行支撑能力。管理员通过后台可维护认证策略、工具审核状态和知识库运行状态，并协调平台基础运行参数，从而保证普通用户看到的功能入口与后端真实可用状态保持一致。
在运行支撑方面，异步文件处理是系统的重要补充链路。知识库文件上传后，并不会在用户前台请求中立即完成解析，而是将任务投递到消息队列，由消费者异步执行文档解析、切分和状态更新。这样既降低了前台请求耗时，也使文件处理过程更易于重试和治理。

尽管系统已经具备较完整的功能闭环，但仍存在进一步完善空间。第一，当前测试以功能正确性验证为主，自动化测试覆盖仍可继续补充；第二，检索增强生成的质量评价目前仍以人工观察为主，后续可以引入更细致的量化指标；第三，外部工具和模型服务仍依赖外部环境稳定性，后续可继续完善超时、重试和运行监控机制。
此外，从测试章节也可以反推出当前系统的两个现实边界。其一，模型质量与工具可用性仍然受到外部服务商稳定性的影响，因此平台侧更适合强调“清晰反馈、隔离失败、保持会话连续性”，而不宜夸大为完全可控的自治系统；其二，知识库问答虽然已经具备混合检索与引用返回能力，但在更大规模文档集上的召回效率与重排效果仍需要通过后续实验进一步量化。
由于本文对应的是本科毕业设计项目，因此测试部分以功能正确性验证为主，不再展开压力测试和大规模性能评估。现有测试结果已经能够说明系统具备基本可用性，并能支撑论文所描述的主要设计与实现内容。
